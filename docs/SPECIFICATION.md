# Taskbot — техническая спецификация (Phase 0)

Источник требований: первоначальная «Taskbot — завершение Phase 0 на основе согласованной спецификации», разделы 1–17, последующие решения по OQ-02 и утверждённое уточнение «Taskbot — Finalize Phase 0 and Prepare for Development». Последнее уточнение имеет приоритет для ролей, регистрации, создания проектов/задач и исключительной приёмки. Нерешённые детали отмечены в [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md). Этот документ не разрешает переход к Phase 1.

## Назначение и границы

Единая внутренняя система управления задачами одной компании. Пользовательские интерфейсы — Telegram-бот и Telegram Mini App на существующем Next.js; отдельной веб-панели или самостоятельного пользовательского сайта нет. Оба клиента используют общую бизнес-логику backend через /api/v1. Multi-tenant архитектура не требуется.

В MVP входят регистрация и подтверждение пользователей, роли и проектный доступ, проекты и спринты, задачи и проверка результата автором, продление сроков, уведомления и личные напоминания, история, базовая аналитика и еженедельный отчёт Super Admin и Team Lead. Интеграция с Notion предусмотрена моделью внешних ссылок, но не реализуется в MVP. Рейтинги, баллы, уровни и таблицы лидеров исключены.

## Согласованная архитектура

| Компонент | Технология / ответственность |
| --- | --- |
| Telegram-бот | Python, aiogram; интерфейс к общему API |
| Backend | Python, FastAPI, Pydantic; единые сервисы и авторизация |
| Telegram Mini App | Next.js, TypeScript; основной интерфейс проектов и задач внутри Telegram |
| Данные | PostgreSQL, SQLAlchemy 2; миграции в будущих фазах только Alembic |
| Worker | Уведомления, напоминания, отчёты, повторные попытки |
| Тесты будущих фаз | pytest |
| Вложения | Приватное S3-совместимое или аналогичное хранилище; в БД только метаданные |

Временные значения в БД хранятся в UTC. Интерфейс и бизнес-отчёты по умолчанию используют Asia/Tashkent. Для сохранения событий и задач доставки нужен transactional outbox либо эквивалент. Redis и брокер очередей не утверждены; базовая рекомендация и сравнение в [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

## Пользователи и доступ

Регистрация начинается в Telegram-боте: пользователь запускает бота, передаёт номер штатной кнопкой «Поделиться контактом», вводит имя и ожидает решения Super Admin. До одобрения существует только заявка/запись Pending без доступа к рабочим данным; после одобрения статус Active. Остальные состояния: Rejected, Blocked. В системе ровно пять фиксированных ролей: Super Admin (один главный администратор), PM (Product Manager), Team Lead (Зарина Равшановна), Предметник-разработчик и QA. У пользователя может быть несколько этих ролей. Индивидуальные разрешения, ACL и дополнительные роли не вводятся. Аккаунт Blocked теряет доступ и действующие сессии отзываются.

Mini App передаёт серверу исходный Telegram.WebApp.initData. Backend проверяет подпись по токену бота, время, структуру и повторное использование proof, затем выдаёт существующую сессию только пользователю Active. Клиентский Telegram ID, initDataUnsafe или номер телефона не являются доказательством. Регистрация и подтверждение контакта остаются в боте; решение о Mini App закрывает OQ-01 в [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

Проекты содержат участников; членство в проекте определяет доступ к задачам, кроме глобально уполномоченного единственного Super Admin. Права определяются фиксированной ролью, проектным членством и правилами автора/исполнителя. Проект создаёт Super Admin или PM по своей фиксированной роли; PM не получает чтения или управления чужими проектами только из-за роли. Team Lead контролирует задачи доступных проектов без административных прав Super Admin. Любой Active участник с доступом к проекту может создать задачу и при создании выбрать одного основного исполнителя из Active участников того же проекта. Если исполнитель ещё не выбран, OPEN ожидает назначения и не может быть принят. Позднее назначение и переназначение выполняет PM доступного проекта; пользователь без проектного доступа не может стать исполнителем. Каждая операция backend заново проверяет права. Матрица — в [PERMISSIONS.md](PERMISSIONS.md).

## Предметная область

Проект: название, описание, владелец, статус, участники. Спринт: проект, название, даты начала и окончания, статус. Задача: UUID, глобально уникальный читаемый task_key, название, описание, неизменяемый created_by, не более одного основного assignee_id, отдельный необязательный qa_reviewer_id и qa_review_status, проект, необязательный спринт, общий статус, приоритет, тип, обязательный дедлайн календарной датой, created_at, completed_at, комментарии, вложения, watchers, зависимости и события истории. Watchers и QA-проверяющий не считаются соисполнителями.

Новая задача создаётся в статусе OPEN. Статус меняется только утверждёнными отдельными операциями; REJECTED сохраняется в истории, а OVERDUE является вычисляемым признаком.

Обычное окончательное принятие результата REVIEW→DONE выполняет неизменяемый автор created_by. Автор отдельно выбирает QA-проверяющего из Active участников проекта с ролью QA. Возврат в REWORK с обязательным комментарием выполняет автор либо назначенный QA; QA фиксирует обнаруженные ошибки и замечания. Успешная проверка QA записывает qa_review_status=DONE, оставляя общий tasks.status=REVIEW и completed_at пустым. Автор вправе принять результат и до QA DONE; при таком завершении проверка не считается пройденной. После общего DONE QA-действия прекращаются. Если автор недоступен, Super Admin выполняет исключительную приёмку отдельным admin-approve: в момент действия он явно подтверждает недоступность автора и указывает обязательную причину. Недоступность не выводится автоматически из отсутствия активности или ответа. Фактический актор, исходный автор, причина, время и факт исключения сохраняются в task_events и audit_logs; created_by не меняется. Другие роли исключение не используют.

Типы: Development, Bug Fix, Improvement, QA/Check, Research. Приоритеты: Urgent, High, Medium, Low. Статусы и операции переходов зафиксированы в [BUSINESS_RULES.md](BUSINESS_RULES.md). OVERDUE является вычисляемым признаком, а не статусом.

Исполнитель может запросить продление с новой датой, причиной и прогрессом. До одобрения действует прежний дедлайн; первоначальный дедлайн и все одобренные изменения сохраняются. Решает автор или уполномоченный менеджер.

## События, уведомления, аналитика

Каждое значимое изменение сохраняется в неизменяемой истории; изменение задачи, история и outbox записываются транзакционно. Уведомления охватывают назначение, отсутствие реакции, контроль дедлайна за 24 и 2 часа, просрочку, продление, проверку, доработку и приёмку. Назначение включает автора, название, описание, дедлайн и кнопки принятия/отказа; отказ требует причину, автор получает сообщение. Через 1 календарный час без ответа получают сообщение автор и все Active Team Lead с проектным доступом без дубля; отдельное напоминание исполнителю — через 4 рабочих часа по календарю понедельник–суббота 10:00–19:00 Asia/Tashkent. При просрочке адресаты — исполнитель и автор. После DONE/CANCELLED неактуальные будущие уведомления прекращаются. Личные напоминания отделены от аналитики задач. Повторы обработки не создают новых логических уведомлений; попытки доставки журналируются. Оставшиеся варианты уведомлений — [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

Аналитика MVP: созданные и принятые за период задачи, активные и просроченные сейчас, ожидающие реакции и проверки, запросы продления, разбивки по проектам и исполнителям, сравнение с предыдущей неделей. Недельный отчёт Super Admin (все проекты) и Team Lead (доступные по членству проекты) запланирован на понедельник 09:00 Asia/Tashkent за предыдущую календарную неделю (понедельник 00:00 — следующий понедельник 00:00, граница справа исключена; это точное представление воскресенья 23:59). PM без одной из этих ролей отчёт не получает. Завершённая задача находится в DONE после обычной авторской либо утверждённой исключительной приёмки Super Admin; показатель «принято автором» учитывает только обычную авторскую приёмку, а исключительная различима отдельно. Основная доля соблюдения сроков использует актуальный одобренный дедлайн среди всех DONE с известным сроком; отдельно вычисляется сравнение с исходным сроком. CANCELLED не завершённая задача. Метрики одинаковы в API, боте, панели и отчёте; определения — в [BUSINESS_RULES.md](BUSINESS_RULES.md).

API и конкретные ответы — в [API.md](API.md), тестовые сценарии — в [TEST_PLAN.md](TEST_PLAN.md).
