# План реализации — результат Phase 0

Источник: согласованная спецификация, разделы 2, 13–17, и последнее утверждённое уточнение о пяти ролях и процессе регистрации/приёмки. Текущий этап — только документация. Следующая фаза начинается после отдельного подтверждения владельца проекта и конкретного плана изменений. Порядок ниже фиксирует согласованные фазы, но не разрешает их выполнять сейчас.

## Архитектурные опоры

Бот и веб-панель — клиенты общего /api/v1; единая бизнес-логика в FastAPI. PostgreSQL хранит предметные данные и UTC-время; SQLAlchemy 2 и Alembic применяются в реализации. Worker обрабатывает отложенные уведомления, напоминания и отчёты. S3-совместимое внешнее хранилище хранит вложения, PostgreSQL — их метаданные. Интерфейс и отчёты используют Asia/Tashkent. Права используют только пять фиксированных ролей, проектное членство и правила created_by/assignee_id; ACL и индивидуальные grants не планируются. Единственный Super Admin и назначение роли Team Lead Зарине Равшановне оформляются только после проверки учётной записи. Изменение задачи, task_event и outbox коммитятся атомарно; фактическая отправка реализуется в Phase 4 по последующему заданию владельца.

Фактический порядок разработки уточнён последующими заданиями владельца: Phase 3 реализовала автомат задач, QA и transactional outbox; Phase 4 реализует worker, уведомления и недельный отчёт. Остальные строки таблицы отражают первоначальный план Phase 0 и не являются перечнем уже выполненных функций. Продление дедлайнов, личные напоминания, сравнение недель и прочая аналитика не должны выдаваться за реализованные в Phase 4. Недельный отчёт адресован только Super Admin и Team Lead с проектной границей, а оповещение об отсутствии ответа через час — автору и доступным Team Lead; отдельное напоминание исполнителю наступает через четыре рабочих часа.

## Выбор транспорта outbox

| Вариант | Польза | Ограничение | Статус |
| --- | --- | --- | --- |
| PostgreSQL transactional outbox + polling worker | Атомарен с задачей, меньше компонентов на старте | Нужны claim/lock, индексы, очистка и мониторинг | Рекомендуемая техническая база, ещё не утверждена |
| PostgreSQL outbox + Redis/broker | Удобен для масштаба и разделения consumers | Дополнительная эксплуатация; публикация всё равно требует надёжного outbox relay | Решать при данных о нагрузке |
| Только Redis/broker без транзакционного outbox | Меньше запросов к БД | Может потерять событие между commit задачи и publish | Не удовлетворяет требованию без эквивалентной атомарной гарантии |

Выбор брокера/Redis не нужен для завершения Phase 0; минимальная рекомендация и технические допущения записаны в [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md). Независимо от транспорта логические уведомления получают уникальный dedupe_key, попытки отправки журналируются, неоднозначные исходы сохраняются.

## Контроль перед каждой будущей фазой

1. Представить владельцу конкретный план изменений в рамках одной фазы и перечень OQ, блокирующих её.
2. Получить отдельное подтверждение этой фазы.
3. Реализовать только согласованный объём; запускать подходящие unit/integration/security проверки.
4. Сообщить фактические результаты, незапущенные проверки, риски и изменение документов.

Phase 0 завершается передачей документации и отчёта. Никакие зависимости, код приложения, миграции, Bot API соединения, реальные ресурсы или инфраструктура сейчас не создаются.
