# Открытые вопросы — Phase 0

Основа: исходная согласованная спецификация, последующие решения по OQ-02, уточнение «Taskbot — Finalize Phase 0 and Prepare for Development» и ответы владельца о выборе исполнителя и QA-проверке. Пять фиксированных ролей, регистрация через бота с одобрением Super Admin, создание проектов Super Admin/PM, создание задач любым Active участником доступного проекта, выбор исполнителя автором при создании, назначение QA автором, отдельный QA DONE и авторская/исключительная окончательная приёмка **решены**. Вопросы ниже относятся только к поведению, которое нельзя однозначно вывести из этих решений. Они не разрешают произвольные роли, индивидуальные grants или ACL.

Открытый вопрос блокирует только затронутое поведение. До ответа действует уже описанное правило; неуказанное право или переход не предоставляется автоматически. Текущий код новых функций требует отдельного решения о применении миграции и запуске против рабочей Supabase.

## Закрытое решение

### OQ-01 Вход в Telegram Mini App — закрыто

Владелец утвердил два интерфейса: бот и Telegram Mini App на существующем Next.js, без отдельной веб-панели. Mini App использует серверную проверку raw Telegram.WebApp.initData, а не OIDC или Login Widget. Backend проверяет HMAC, auth_date, replay и существующий Active аккаунт; затем выдаёт существующую отзывную cookie-сессию и CSRF token. При регистрации контакт по-прежнему принимается только из Telegram update и при совпадении contact.user_id с from.id. Legacy Login Widget API оставлен для совместимости, но Mini App его не вызывает.

## Решения и остаточные вопросы

### OQ-02 Границы управления проектом — Phase 2/3

Подтвердить, может ли PM, имеющий доступ к проекту, менять состав участников и метаданные проекта; если да, какие ограничения действуют при исключении участника с назначенной задачей? Утверждено: Super Admin и PM создают проект, PM без членства не видит и не управляет чужими проектами; права определяются фиксированной ролью и членством. Индивидуальный грант project.create не нужен. До решения состав и метаданные меняет только Super Admin. При создании проекта создатель получает членство для работы в нём и становится владельцем по умолчанию; это техническое следствие проектной границы. Изменение глобальных пользователей/ролей остаётся только у Super Admin. Возможность дополнительных администраторских действий Super Admin над задачей, кроме отдельного admin-approve, не предполагается.

### OQ-03 Переходы статуса аккаунта — Phase 2

Помимо утверждённого Pending→Active после одобрения и потери доступа при Blocked, разрешены ли повторная заявка после Rejected и разблокировка Blocked? Кто выполняет эти действия и требуется ли причина? До решения такие переходы не предлагаются пользователю. Инвариант одного действующего Super Admin сохраняется.

### OQ-04 Участки жизненного цикла задачи — Phase 3/4

Что происходит после REJECTED при переназначении: допускается ли повторное назначение тому же исполнителю, какой утверждённый статус следует после переназначения? Что считать активной задачей для отчётов? Обязателен ли отдельный результат при IN_PROGRESS→REVIEW и в каком формате? В Phase 3 владелец разрешил отмену из OPEN, ACCEPTED, REJECTED, IN_PROGRESS, BLOCKED, REVIEW и REWORK с обязательной причиной; из DONE/CANCELLED обратных переходов нет. Уже утверждённые переходы, обязательные комментарии и стартовый OPEN не меняются.

### OQ-05 Сроки и просрочка — частично закрыто

Дедлайн обязателен и задаётся календарной датой (поля due_date, original_due_date и current_due_date). OVERDUE вычисляется с 00:00 следующего календарного дня в Asia/Tashkent для OPEN, ACCEPTED, IN_PROGRESS, BLOCKED и REWORK; REVIEW, REJECTED, DONE и CANCELLED исключены. Владелец утвердил **не более одного Pending запроса продления на задачу**. До одобрения current_due_date не меняется, original_due_date и история одобренных изменений сохраняются. Осталось решить, допускается ли срок в прошлом и кто может менять его напрямую помимо процесса запроса.

### OQ-06 Состояние проектов и спринтов — частично закрыто

Владелец утвердил даты спринта как **календарные даты Asia/Tashkent, без статуса спринта**. Открыты статусы и переходы проекта, архивирование проекта и действие при исключении участника с активной задачей. Эти вопросы не блокируют создание и отображение спринтов.

### OQ-07 Зависимости задач — закрыто в части MVP

Владелец утвердил: зависимости разрешены **только внутри одного проекта** и **не блокируют переходы статуса**. Самоссылки и циклы запрещены, скрытые проекты не раскрываются. Удаление связи не входит в текущий контракт.

### OQ-08 Оставшиеся варианты уведомлений — после Phase 4

Утверждено: через 1 календарный час без ответа уведомляются автор и все Active Team Lead системы, без дубля одному человеку; роль PM сама по себе не является адресатом. Отдельное напоминание исполнителю наступает через 4 накопленных рабочих часа с назначения: понедельник–суббота 10:00–19:00 Asia/Tashkent, без праздников. Оба отсчёта прекращаются после принятия, отказа, отмены или переназначения и начинаются заново при переназначении. Назначение содержит автора, название, описание, срок и кнопки; отказ требует причину в истории, автор получает уведомление. Напоминания за 24 и 2 часа и просрочку получают исполнитель и автор без дублей. Запрос продления получает автор задачи, решение — исполнитель. Открыты поведение, когда дедлайн наступает вскоре после создания/изменения задачи, политика тихих часов и дальнейшие повторы просрочки. Retry и канал доставки — техническая политика с журналированием попыток и без обещания физической exactly-once доставки Telegram.

### OQ-10 Хранение истории и персональных данных — до эксплуатации

Какие сроки хранения телефона, task_events, audit_logs, попыток уведомлений и вложений, и как удовлетворять запросы удаления персональных данных при обязательной истории? Обычный пользователь не может править историю; архивирование не стирает связанные события автоматически. До решения нельзя вводить физическое удаление истории или политику хранения данных в эксплуатации.

### OQ-11 Оставшиеся вопросы аналитики — после Phase 4

Как отображать долю при нулевом знаменателе и распределять результат после переназначения между исполнителями? Владелец добавил PM к получателям недельного отчёта: Active Super Admin и Team Lead видят все проекты, Active PM — только доступные ему проекты, через Telegram и API. Состав метрик, понедельник 09:00 Asia/Tashkent, период предыдущей недели, различение AUTHOR/ADMIN_OVERRIDE и расчёт срока по всем DONE уже зафиксированы. Историческое сравнение следует строить as-of по событиям либо по согласованным снимкам; выбор хранения — технический.

### OQ-12 Вложения — закрыто для MVP

Владелец утвердил **приватный Supabase Storage**, PDF/PNG/JPEG/TXT до **10 МБ**. Удаление разрешено автору вложения или Super Admin, с аудитом. Backend проверяет право чтения задачи перед выдачей краткоживущей ссылки; публичный bucket не допускается. Технический поток — ограниченная серверная загрузка через API.

## Технические допущения без изменения бизнес-правил

- Обычные изменяющие API-операции требуют Idempotency-Key; вход Mini App защищён проверкой подписи initData, срока и одноразовости proof; для webhook действуют проверка источника и дедупликация update_id. Срок хранения ключей, cursor cap и retry budget настраиваются при реализации и документируются перед запуском.
- PostgreSQL transactional outbox с worker — минимальная рекомендуемая реализация атомарной записи события и intent уведомления. Redis/брокер не обязателен без данных о нагрузке; это не ослабляет требование надёжной доставки и дедупликации.
- Одинаковый expected_version/If-Match механизм будет выбран для всех конкурентных мутаций перед кодированием API. До этого контракт показывает expected_version.
- Личные уведомления и напоминания доступны только их получателю/владельцу. Неутверждённые расширения чтения полного audit_log, проектных отчётов или мутаций чужой задачи не предоставляются по умолчанию.
- Создание проекта PM не открывает существующие проекты; создатель становится членом создаваемого проекта. Роль Team Lead даёт просмотр всех проектов и задач и создание задачи в любом существующем проекте, без административных операций Super Admin.

## Закрытые противоречия

| Было | Зафиксировано |
| --- | --- |
| Четыре роли и индивидуальные разрешения | Ровно пять фиксированных ролей, множественные роли пользователя и project_members; ACL/grants отсутствуют. |
| Создание проекта только Super Admin или через особый project.create | Super Admin и PM создают проекты по фиксированной роли; PM не видит чужие проекты автоматически. |
| Создание задач только PM | Любой Active участник доступного проекта создаёт задачу и может сразу выбрать исполнителя из Active участников проекта; позднее назначение/переназначение выполняет PM. |
| Автор не мог выбрать исполнителя при создании | Автор может выбрать одного Active участника проекта при создании; при отсутствии выбора OPEN ждёт позднего назначения PM. |
| Неясное право QA на возврат и приёмку | Автор выбирает QA-проверяющего из Active участников проекта с ролью QA; назначенный QA может вернуть REVIEW→REWORK с обязательным комментарием либо отметить отдельный QA DONE без изменения общего REVIEW. Автор может выполнить окончательное approve и до QA DONE; незавершённая QA-проверка не считается пройденной. |
| Неопределённый начальный статус | Новая задача всегда OPEN. |
| Недоступность автора нужно выводить из его активности | Super Admin сам явно подтверждает недоступность в отдельном admin-approve, указывает причину; автор не меняется, актор и обстоятельства сохраняются в task_events и audit_logs. |
| Отсутствовал endpoint BLOCKED→IN_PROGRESS | Добавлен POST /tasks/{id}/resume для утверждённого перехода. |
| DONE мог подавить своё уведомление | Подавляются устаревшие запланированные напоминания; уведомление о приёмке сохраняется. |
| «Воскресенье 23:59» неоднозначно для субсекунд | Неделя представлена интервалом [Пн 00:00, следующий Пн 00:00) в Asia/Tashkent. |

Не включено в MVP: Notion-интеграция (кроме задела ссылок), баллы, рейтинги, уровни и лидерборды. QA уже входит в пять утверждённых ролей.
