# Taskbot deployment runbook

This is a launch sequence, not an automatic deployment. The database is the existing Supabase PostgreSQL. DEMO is a normal project; do not filter or clear its tasks, outbox, notifications or reports. Migrations `0006_mvp_entities` and `0007_restrict_data_api` are prepared in the repository but have **not** been applied to Supabase. The production services must not start on the old schema. Remaining decisions and unverified external flows are recorded in `MVP_REQUIREMENTS.md` and `OPEN_QUESTIONS.md`.

## Required configuration

Provide secrets through the runtime's secret store, never through `NEXT_PUBLIC_*` or a committed file. Use one bot token for polling, Mini App signature verification and Telegram delivery.

| Process | Required values | Conditions |
| --- | --- | --- |
| API | `TASKBOT_DATABASE_URL`, `TASKBOT_BOT_TOKEN`, `TASKBOT_WEB_ORIGIN`, `TASKBOT_APP_ENV=production`, `TASKBOT_SESSION_COOKIE_SECURE=true`, `TASKBOT_DEV_LOGIN_ENABLED=false`, `TASKBOT_SUPABASE_URL`, `TASKBOT_SUPABASE_SECRET_KEY`, `TASKBOT_ATTACHMENT_BUCKET` | Database URL uses `postgresql+asyncpg`. Web origin is the exact public HTTPS Mini App origin without trailing `/`. Storage bucket must exist and be private; secret key is server-only. |
| Vercel Next.js Mini App | `TASKBOT_API_UPSTREAM`, `NEXT_PUBLIC_TASKBOT_DEV_LOGIN_ENABLED=false` | `TASKBOT_API_UPSTREAM` is the server-only permanent HTTPS origin of the deployed API and must be present at build time. Do not set `NEXT_PUBLIC_TASKBOT_API_URL`. `/api/v1/*` is proxied by Next.js. |
| Telegram bot | `TASKBOT_DATABASE_URL`, `TASKBOT_BOT_TOKEN`, `TASKBOT_WEBAPP_URL`, `TASKBOT_APP_ENV=production` | WebApp URL is the reachable public HTTPS Mini App URL. Run one polling instance. |
| Worker | `TASKBOT_DATABASE_URL`, `TASKBOT_BOT_TOKEN`, `TASKBOT_NOTIFICATION_DELIVERY_ENABLED`, `TASKBOT_NOTIFICATION_TRANSPORT` | Keep delivery disabled until the pending queue and recipients have been reviewed and real delivery has been explicitly authorized. `dry_run` records simulated delivery when delivery is enabled. |

The API, bot and Worker also read optional timeout, session, retry and working-calendar settings from `.env.example`. Keep `TASKBOT_WEBAPP_URL` and `TASKBOT_WEB_ORIGIN` aligned to the same public Mini App host. A Quick Tunnel is temporary and is not a production URL. The current local `apps/web/.env.local` points to a loopback HTTP API; set `TASKBOT_API_UPSTREAM` **in the deployment environment** to the real, permanent HTTPS API origin before building Next.js. `next.config.ts` rejects HTTP in a production build. No API URL or hostname is inferred by the application. Do not set `NEXT_PUBLIC_TASKBOT_API_URL` or expose Supabase credentials to Next.js or the browser.

The existing `allowedDevOrigins` entry in `apps/web/next.config.ts` is for a local Quick Tunnel in Next.js development mode; it is not the production Mini App URL or the production API upstream. Preserve that local user setting. Production routing depends only on the Vercel environment's `TASKBOT_API_UPSTREAM` and the permanent domain attached to the Vercel project.

Before deployment, the operator must supply two permanent DNS names with valid HTTPS certificates: the public Mini App origin and the public API origin. Supply the existing Supabase PostgreSQL connection string to the server processes, the existing Telegram bot token to the API/bot (and Worker only when Telegram delivery is enabled), the Supabase project API origin and a server-only secret key to the API, and the chosen private attachment bucket name. These are deployment secrets/settings, not values to commit. `TASKBOT_WEBAPP_URL` and `TASKBOT_WEB_ORIGIN` use the Mini App origin; `TASKBOT_API_UPSTREAM` uses the distinct API origin. Telegram BotFather's Menu Button must use the same Mini App URL. Confirm the API origin is reachable from the Next.js server and that its certificate is trusted.

## Migration gate: current database and access control

On 2026-10-20, a read-only connection through the project's configured `TASKBOT_DATABASE_URL` showed Alembic `0005_outbox_retry`, 16 tasks including 13 in DEMO, and neither the `0006` tables nor `tasks.sprint_id` / `notifications.read_at`. The existing `outbox_events.attempts` column is `NOT NULL DEFAULT 0`; `last_error_code` is nullable. `0006_mvp_entities` depends directly on `0005`; it creates nine tables, indexes and foreign keys, adds nullable `tasks.sprint_id` and `notifications.read_at`, and does not delete or update existing rows. New-table required fields have ORM-side defaults where applicable, **not database server defaults**; they are empty on upgrade, so this does not require backfilling old rows. Its downgrade drops the new tables and both columns and would destroy data created after upgrade; use a verified backup and forward repair rather than relying on downgrade for data recovery.

**Do not apply the migrations without the owner's separate approval.** The read-only check found that existing Taskbot tables in `public` (including `users`, `tasks`, `projects`, `notifications`, `outbox_events` and audit/history tables) have RLS disabled and `anon`/`authenticated` table grants. `0007_restrict_data_api` is the prepared security migration: it enables RLS without public policies and revokes those two roles on every Taskbot table, including the `0006` tables. It also removes the migration role's default `public` table grants to those roles. The application uses a trusted direct PostgreSQL connection whose observed role is `postgres` with `BYPASSRLS`; it does not use Supabase's Data API for Taskbot data. The migration's downgrade intentionally refuses to reopen direct access. Confirm the project's Data API exposed-schema setting and review this access model before approval; no live grants or RLS were changed during preparation. See [Supabase's RLS and grant guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Launch order

1. Choose reachable permanent HTTPS origins for the API and Mini App. Confirm the existing Supabase backup/recovery point and Storage object backup plan. Provision the existing credentials through server-only environment stores. Review the Data API setting and the `0007` security change. Verify the live revision with `python -m alembic current`; it was `0005_outbox_retry` at the last read-only check.
2. After **separate approval for the database change**, stop application writes and keep Bot and Worker off. From the checked-out repository root with the production `TASKBOT_DATABASE_URL`, run exactly `python -m alembic upgrade 0007_restrict_data_api`. Alembic's PostgreSQL transaction covers `0006` and `0007` in this single upgrade command. Do not run `alembic upgrade` automatically at service startup. Confirm `python -m alembic current` reports `0007_restrict_data_api`, verify task/DEMO counts and RLS/grants, and only then restart updated services. A failed upgrade must be investigated before serving traffic; do not downgrade the security migration.
3. Install Python 3.11+ dependencies on the server from the repository root with `python -m venv .venv` then `.venv/bin/python -m pip install -e .`. Run backend tests in a safe environment and `.venv/bin/python -m taskbot_bot --check` / `.venv/bin/python -m taskbot_worker --check`; these check commands do not start polling or process the queue. Run each long-lived process under a service manager with automatic restart, a dedicated OS user, a protected working directory, and server-only environment variables loaded from the host secret store. Use these process commands from the repository root:

   | Service | Process command | Exposure |
   | --- | --- | --- |
   | API | `.venv/bin/python -m uvicorn taskbot_api.main:app --host 127.0.0.1 --port 8000` | Reverse proxy terminates HTTPS at the permanent API origin and forwards to loopback. |
   | Bot | `.venv/bin/python -m taskbot_bot` | One polling instance per bot token; no public inbound port required. |
   | Worker | `.venv/bin/python -m taskbot_worker --run` | Start **only after separate queue-processing approval**; no public inbound port required. |

   Configure three supervised services (for example systemd on Linux) with repository `WorkingDirectory`, absolute `.venv/bin/python` `ExecStart`, `Restart=always`, and a protected `EnvironmentFile` or secret-store injection. Do not use Vercel Functions for the continuously polling bot or Worker. Do not place the API's secrets in Vercel. Check the API through its public `GET /api/v1/health` and `/api/v1/health/ready`; only readiness tests PostgreSQL.
4. In Vercel import the repository as **one Next.js project with Root Directory `apps/web`**. Keep the framework's `npm ci` install and `npm run build` build commands. In **Production** environment settings set server-only `TASKBOT_API_UPSTREAM` to the real API HTTPS origin and set `NEXT_PUBLIC_TASKBOT_DEV_LOGIN_ENABLED=false`; leave `NEXT_PUBLIC_TASKBOT_API_URL`, database URL, bot token and Storage secret unset. Attach the permanent Mini App HTTPS domain. The existing Next.js rewrite sends `/api/v1/*` to the server-side upstream. Build only after the API origin is known; do not substitute localhost or a Quick Tunnel. Check Mini App `/` and `/api/v1/health/ready` through the Vercel domain, and confirm protected endpoints reject unauthenticated requests. See [Vercel monorepo root-directory setup](https://vercel.com/docs/monorepos) and [build environment settings](https://vercel.com/docs/builds/configure-a-build).
5. Set the bot's `TASKBOT_WEBAPP_URL` to the Mini App HTTPS URL and the API's `TASKBOT_WEB_ORIGIN` to the same origin without trailing slash. In BotFather use **Bot Settings → Menu Button → Open → URL → Save** with the same URL; configure the profile Launch app entry separately if enabled. Start the supervised bot after DB/API readiness. Startup also calls `setChatMenuButton`; a new `/start` response contains an inline WebApp button. Verify approved-user `initData` login and pending/rejected denial inside Telegram.
6. Inspect all existing outbox and notification records and intended recipients, including DEMO. Only after authorizing queue processing, start one supervised Worker. Delivery remains off while `TASKBOT_NOTIFICATION_DELIVERY_ENABLED=false`; the Worker may still change outbox and scheduled records. For a simulated send use enabled delivery with `TASKBOT_NOTIFICATION_TRANSPORT=dry_run` only after accepting that it marks messages simulated. Enable `telegram` transport and real delivery only after a separate explicit go-live decision. Observe attempts, failures, retry backlog and weekly report generation.

Do not start another polling bot against the same token or process the live Worker queue while testing. An ambiguous Telegram send timeout can still produce a duplicate on retry. Verify the live Mini App `initData` sign-in, cookie/CSRF flow, BotFather button, and one controlled notification inside Telegram; local unit tests and a Next.js build cannot prove those external flows.

## Backup and recovery

Before any schema change, open the **correct** Supabase project's **Database → Backups** page. Record the latest completed daily backup timestamp or, if PITR is enabled, the available recovery-point range and a recovery point immediately before the change. Record the project reference and backup type. Do not treat the existence of the Backups page as proof of a completed backup. Supabase daily backups are plan-dependent; physical backups may not be downloadable. If there is no suitable completed restore point, create a separate logical export before approval. See [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups) and [Supabase backup/restore CLI procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).

For an independent pre-change copy of **Taskbot's `public` schema and data**, use a PostgreSQL `pg_dump` client compatible with the server major version (currently PostgreSQL 17). The operator obtains host, port and username from Supabase **Connect**, loads the password into `PGPASSWORD` from a trusted secret store, then runs the following from a protected directory **outside this repository**. Set the three PowerShell variables to the actual values first; do not paste a password into the command line or a tracked file:

```powershell
$PoolerHost = 'HOST_FROM_SUPABASE_CONNECT'
$DbUser = 'USER_FROM_SUPABASE_CONNECT'
$BackupFile = 'ABSOLUTE_PROTECTED_PATH_OUTSIDE_REPO\taskbot-before-0006.dump'
pg_dump --host $PoolerHost --port 5432 --username $DbUser --dbname postgres --schema public --format custom --no-owner --no-acl --file $BackupFile
if ($LASTEXITCODE -ne 0) { throw 'pg_dump failed' }
pg_restore --list $BackupFile | Select-Object -First 10
if ($LASTEXITCODE -ne 0) { throw 'Backup archive verification failed' }
Remove-Item Env:PGPASSWORD
```

This scoped dump contains the Taskbot tables and `alembic_version`; it is **not** a full Supabase project backup. Retain it encrypted with access controls and verify a restore on an operator-approved isolated target before relying on it. `pg_dump` and the Supabase CLI were not available on the checked machine, and no dump or Dashboard backup was confirmed during this review. A database backup contains Storage metadata, not object bytes. Export private bucket objects separately using the [Supabase Storage download procedure](https://supabase.com/docs/guides/storage/management/download-objects); at review time `storage.buckets` and `storage.objects` were both empty in the connected project. Do not delete or alter the DEMO project.

Document the Alembic revision, backup timestamp, object backup location, and a responsible operator. Practice restoring the database and private objects to a controlled recovery target before production launch. Restore the database and bucket from matching points in time, run `alembic current`, check task/attachment counts and `/api/v1/health/ready`, then verify an authorized attachment download. A production restore is an operator-approved incident action; it is never part of app startup or automated tests.

## Private attachment bucket

In the **same** Supabase project, open **Storage → New bucket**. Set the name to `taskbot-attachments`, **Public bucket = off**, maximum file size **10 MiB / 10,485,760 bytes**, and allowed MIME types `application/pdf`, `image/png`, `image/jpeg`, `text/plain`. Confirm the bucket remains private in Storage settings. The API checks this through Storage before every upload or signed download and issues 60-second links only after task authorization; do not add public read policies. The bucket is an owner-created external resource; no bucket was created during release preparation. See [Supabase bucket settings](https://supabase.com/docs/guides/storage/buckets/creating-buckets) and [private bucket access](https://supabase.com/docs/guides/storage/buckets/fundamentals).

In the API's server-side secret store set `TASKBOT_SUPABASE_URL` to this project's `https://<project-ref>.supabase.co` origin, `TASKBOT_SUPABASE_SECRET_KEY` to its server-only Supabase secret key (or the legacy service-role key if that is the project's supported credential), and `TASKBOT_ATTACHMENT_BUCKET` to the chosen name. `attachment_storage.py` uses the secret only on the API server. Keep all three out of Next.js `NEXT_PUBLIC_*` variables, Git and Telegram messages. The API requires all three together and rejects a public bucket. After authorization to operate on production data, verify an upload, authorized signed download and unauthorized rejection with a small allowed test file; none was performed in this review.

## Smoke checks

Verify API health and readiness, frontend root and proxy health, unauthenticated rejection of protected API, approved Telegram `initData` login, blocked/pending denial, CSRF rejection, project and task visibility by role, private attachment download and deletion permissions, deadline request history, and weekly report scope. Leave delivery disabled and Worker stopped until the existing outbox, including DEMO, has been reviewed and a separate real-delivery decision is made.
